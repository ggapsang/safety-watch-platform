# AI Vision 통합관제 대시보드

네트워크 카메라(한화비전) 영상을 웹으로 스트리밍하고, 카메라가 발행하는 ONVIF 이벤트를
받아 안전 이벤트로 적재·조회·통계하는 관제 시스템입니다.

```
 [네트워크 카메라] ---RTSP--------> [server] ---MJPEG---> [브라우저]
        |                             |  |
        +---MQTT(ONVIF 이벤트)--> [mosquitto]  +-- WebSocket 푸시(새 이벤트·카메라 상태)
                                      |
                                 [postgres]
                                      |
                                      +-- 브라우저가 브로커에 직결 구독 (MQTT 로그 화면)
```

## 빠른 시작

```bash
cd aivision/deploy
cp .env.example .env
# SECRET_KEY 생성 후 .env 에 붙여 넣습니다 (카메라 비밀번호 암호화 키)
python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"

docker compose up -d --build
```

브라우저에서 `http://localhost:11880` 을 엽니다. 처음에는 카메라가 없으므로
**관리자 → 카메라 등록**에서 현장 카메라의 IP 를 등록합니다.

| 항목 | 주소 | 비고 |
|---|---|---|
| 대시보드 | `http://<서버IP>:11880` | |
| API 문서 | `http://<서버IP>:11880/api/docs` | |
| MQTT (카메라 → 서버) | `<서버IP>:1883` | 카메라의 MQTT 발행 대상(표준 포트) |
| MQTT WebSocket (브라우저) | `<서버IP>:11881` | 'MQTT 로그' 화면 직결 구독 |
| PostgreSQL | `<서버IP>:11882` | 분석·점검용 직접 조회 |
| **RTSP (분석 모듈)** | `rtsp://<서버IP>:8554/cam/{id}` | 모듈이 영상을 가져가는 곳 |
| 미디어 WebRTC / HLS | `<서버IP>:11884` / `:11885` | 브라우저 저지연 재생(현재 미사용) |

> 8080·5432 는 다른 프로그램과 자주 부딪혀 118xx 대역으로 옮겼습니다.
> **MQTT TCP 만 표준 1883 을 그대로 씁니다** — 카메라 기본값이라 여기를 옮기면 현장
> 카메라마다 설정을 바꿔야 하기 때문입니다.
> 컨테이너 안쪽은 어느 쪽이든 표준 포트라, 서버는 여전히 `mqtt:1883` · `db:5432` 로 붙습니다.
>
> 이 PC 에 Mosquitto 를 따로 설치한 적이 있다면 1883 을 이미 점유하고 있을 수 있습니다.
> `netstat -ano | findstr :1883` 으로 확인하고, 있다면 그 서비스를 먼저 내려야 합니다.

> 주의: 다른 PC 에서 접속시킬 계획이라면 `deploy/.env` 의 `MQTT_WS_URL` 을 `ws://localhost:11881` 이 아니라
> **서버 PC 의 IP** 로 바꿔야 합니다. 'MQTT 로그' 화면은 브라우저가 브로커에 직접 붙습니다.

## 카메라 등록

필요한 것은 **IP 하나**입니다. 계정·비밀번호는 카메라가 인증을 요구할 때 넣고,
포트와 스트림 경로는 기본값(554, `/profile2/media.smp`)을 그대로 쓰면 됩니다.
이름과 설치 위치를 비워 두면 IP 로 채웁니다.

**연결 테스트** 버튼은 실제로 RTSP 를 열어 첫 프레임을 받아 보고 해상도를 알려 줍니다.

비밀번호는 `SECRET_KEY` 로 암호화해 저장하며 API 응답에 실리지 않습니다.

## 미디어 평면 — fan-out · 녹화

카메라 펌웨어는 동시 RTSP 세션을 보통 5~10 개로 제한합니다. 대시보드 2명 + 분석 모듈 2개 +
녹화면 이미 한계입니다. 그래서 **카메라에서는 한 번만 당기고** 나머지는 전부 미디어 서버에서
가져갑니다.

```
[카메라] --RTSP 1개 세션--> [MediaMTX] --+--> 서버 워커 (스냅샷 · MJPEG)
                                        +--> 분석 모듈 (RTSP)
                                        +--> 디스크 (녹화)
```

분석 모듈이 영상을 가져갈 주소는 카메라 목록 API 의 `rtsp_url` 로 내려갑니다
(`rtsp://<서버>:8554/cam/{id}`).

미디어 서버 자신도 어댑터입니다. 코어는 `MediaBackend` 만 알고 MediaMTX 는 그 구현 하나입니다
(`MEDIA_BACKEND=direct` 로 바꾸면 미디어 서버 없이 카메라에 직접 붙습니다 — fan-out·녹화 없음).
미디어 서버가 죽으면 자동으로 카메라 직접 접속으로 되돌아갑니다.

### 녹화 책임 분리

| 관심사 | 책임 |
|---|---|
| 세그먼트 파일 쓰기 · 회전 삭제 · 구간 재생 | 미디어 서버 |
| 무엇을 언제 녹화할지 (카메라별 on/off · 보존일수) | 코어 |
| 이벤트 클립 추출과 소유 | 코어 |

**이벤트 클립은 별도 파일로 복사해 옵니다.** 세그먼트에 참조만 걸어 두면 보존기간이 지나
회전 삭제될 때 사고 영상이 같이 사라집니다. 상시 녹화는 며칠, 사고 클립은 길게 — 보존 정책이
다르기 때문입니다.

## 지금 어디까지 되어 있나

동작하는 것:

- 카메라 등록(IP 하나로) · 온오프라인 감시 · 연결 테스트
- 미디어 fan-out (카메라 1세션 -> 다중 소비자), 상시 녹화, 타임라인 조회, 구간 재생
- 이벤트 발생 시 스냅샷과 **영상 클립**(전후 10초) 자동 보관
- **인바운드 바인딩** — 어떤 토픽·페이로드든 코드 없이 이벤트로 변환 (MQTT · HTTP)
- **분석 모듈 레지스트리** — 등록 · 카메라 할당 · 일감 수령 · heartbeat
- **라이브 박스 오버레이** — 영상 위에 실시간 박스 (이벤트로는 쌓지 않음)
- MQTT 원문 수신·보관 ('MQTT 로그' 화면), 이벤트 적재·조회, CSV 내려받기

아직 비어 있는 것:

- **탐지 항목(무엇을 이벤트로 볼지)** — 정해지지 않아 기본값을 심지 않았습니다.
  그럴듯한 항목을 미리 넣어 두면 현장과 맞지 않는 것을 나중에 지우는 일부터 해야 합니다.
- **심각도·처리 상태** — 같은 이유로 넣지 않았습니다. 컬럼도 만들지 않았습니다.
- **통계 화면** — 조회 조건과 골격만 있고 지표는 비어 있습니다. 서버의 `/api/stats` 는
  시계열·카메라별 집계를 이미 내려주므로 지표가 정해지면 붙이기만 하면 됩니다.
- **서버 YOLO** — 자리와 계약만 잡혀 있습니다(`detection/yolo_source.py`).
- **아웃바운드 어댑터** — 웹훅 · 알림 · PLC 로 내보내는 통로.

## 분석 모듈을 붙일 때

코어는 모듈이 **어디서 도는지 모릅니다.** 서버 프로세스 안이든 옆 컨테이너든 다른 PC 든
카메라 안이든, 결과만 같은 문으로 들어오면 됩니다.

모듈이 하는 일은 셋뿐입니다.

```bash
# 1. 등록 (같은 id 로 다시 부르면 갱신 — 재시작할 때마다 실패하면 곤란하다)
curl -X POST localhost:11880/api/modules -H 'Content-Type: application/json'   -d '{"id":"yolo-ppe","name":"PPE 판독","kind":"sidecar","capabilities":["ITEM-001"]}'

# 2. 무엇을 볼지 물어본다 -> 카메라별 RTSP 주소와 옵션을 받아 간다
curl localhost:11880/api/modules/yolo-ppe/work
#  {"items":[{"camera_id":4,"rtsp":"rtsp://mediamtx:8554/cam/4","options":{"min_conf":0.5}}]}

# 3. 판정 결과를 보낸다 — MQTT 발행 또는 HTTP
curl -X POST localhost:11880/api/ingest -H 'Content-Type: application/json'   -d '{"topic":"aivision/detect/4/yolo-ppe","payload":{"camera_id":4,"item":"ITEM-001",
       "confidence":0.88,"boxes":[{"x1":0.1,"y1":0.2,"x2":0.3,"y2":0.6}]}}'
```

카메라 할당은 관리자가 정합니다(`POST /api/modules/{id}/assignments`). 옵션(ROI·스케줄·
임계값)은 JSON 이고 **코어는 그 내용을 해석하지 않습니다** — 모듈에 그대로 넘깁니다.
코어가 탐지 파라미터를 이해하기 시작하면 매니페스토 2번이 깨집니다.

모듈에는 **카메라 IP 나 계정을 주지 않습니다.** 미디어 서버 주소만 주므로 카메라 부하도
늘지 않습니다.

### 라이브 박스와 이벤트는 다른 길로 갑니다

| | 이벤트 | 라이브 박스 |
|---|---|---|
| 빈도 | 가끔 | 초당 여러 번 |
| 영속 | 한다 (스냅샷·클립 첨부) | 안 한다 |
| 경로 | 바인딩 -> 승격 -> DB -> WebSocket | 바인딩 -> WebSocket (통과만) |

바인딩에서 **라이브 전용**을 켜면 같은 매핑 문법을 쓰면서 적재를 건너뜁니다.
초당 수십 건을 이벤트 파이프에 태우면 DB 가 감당하지 못합니다.

## 새 소스를 받아들일 때 — 인바운드 바인딩

무엇을 이벤트로 볼지는 코드가 아니라 **DB** 에 있습니다.
**우리 토픽 규약은 특권이 아닙니다** — 협력사가 정한 임의 토픽도 등록하면 똑같이 동작합니다.

1. **MQTT 로그** 화면에서 실제로 어떤 토픽·페이로드가 오는지 봅니다.
   바인딩에 안 걸린 메시지도 전부 보관되므로 모르는 토픽도 일단 보입니다.
2. 메시지를 눌러 **바인딩 만들기** 를 누르면 그 토픽·페이로드가 시험 화면으로 넘어갑니다.
3. `solutions` 에 탐지 항목을 넣고, 관리자 → **인바운드 바인딩** 에서 규칙을 만듭니다.
4. '시험' 으로 걸리는지 확인합니다. 안 걸리면 사유를 알려 줍니다.

전송 방식은 MQTT 와 HTTP 둘입니다. **둘 다 같은 바인딩 층을 지납니다** — 전송이 다르다고
특별 대우를 받지 않습니다. MQTT 를 못 쓰는 모듈은 `POST /api/ingest` 로 토픽과 페이로드를
그대로 밀어넣으면 됩니다.

바인딩은 두 부분입니다.

| | 내용 |
|---|---|
| 무엇이 걸리는가 | 토픽 패턴(MQTT 와일드카드) + 페이로드 조건 |
| 어떻게 뽑는가 | 카메라 · 탐지항목 · 상태 · 신뢰도 · 박스를 각각 표현식으로 |

표현식 문법은 넷뿐입니다 — `$.a.b`(페이로드) · `$topic[2]`(토픽 조각) · `$mac` · 리터럴.
페이로드 형식으로 `onvif` 를 고르면 ONVIF 의 `SimpleItem` 배열을 평면 키로 펴 줍니다.
박스는 픽셀·정규화·중심좌표 어느 형식으로 와도 **0~1 정규화로 통일해** 저장합니다.

## 구조

```
aivision/
├─ deploy/            docker-compose · Dockerfile · mosquitto 설정 · .env
│                    (compose 는 자기 디렉터리의 .env 를 자동으로 읽습니다)
├─ server/            FastAPI 백엔드
│  ├─ migrations/     Alembic 스키마 이력
│  └─ aivision_server/
│     ├─ models.py        DB 스키마 (카메라·탐지항목·바인딩·이벤트·녹화·MQTT 로그·설정)
│     ├─ media/           미디어 백엔드 계약 + MediaMTX 구현 (fan-out·녹화·재생)
│     ├─ mqtt/mapping.py  인바운드 매핑 — 어떤 모양의 메시지든 정규형으로
│     ├─ detection/       탐지 소스 (인터페이스 + MQTT 인바운드 + YOLO 껍데기)
│     ├─ streaming/       프레임 워커 · MJPEG 재송출
│     ├─ services/        바인딩 엔진, 이벤트 승격, 녹화 정책, 통계, 감시, 푸시 버스
│     └─ api/modules.py   분석 모듈 등록·할당·일감, api/ingest.py HTTP 인바운드
│     └─ api/             REST · WebSocket 라우터
└─ web/               React + Vite + Tailwind v4 프론트엔드
   └─ src/pages/      종합 현황 · 카메라 · 이벤트 · 통계 · MQTT 로그 · 관리자
```

### 설계상 지켜야 할 경계

**1. 탐지 소스는 갈아 끼울 수 있어야 합니다.**
판정이 카메라 엣지(MQTT)에서 오든, 서버 YOLO 에서 오든, 나중에 외부 서비스에서 오든
`DetectionSignal` 이라는 같은 모양으로 들어오고 그 뒤 처리는 완전히 동일합니다.
소스를 추가할 때 손대는 곳은 `detection/` 과 `registry.py` 뿐이며 API·DB·프론트는 그대로입니다.

**2. 영상과 박스는 다른 채널로 갑니다.**
서버는 프레임에 바운딩 박스를 굽지 않습니다. 영상은 MJPEG(`<img>`), 박스는 WebSocket JSON 으로
따로 가고 브라우저가 SVG 로 겹칩니다. 그래서 판정이 늦게 도착해도 어긋나지 않고,
나중에 전송 방식을 바꿔도 오버레이 코드는 그대로이며, 한글 라벨이 깨지지 않습니다.

**3. 박스 좌표는 0~1 정규화로만 저장합니다.**
카메라 해상도가 섞이고, 엣지 추론은 640 입력 좌표계로 뱉고, 화면은 CSS 픽셀 위에 그립니다.
픽셀로 저장하면 변환 지점이 세 군데로 흩어집니다.

**4. 환경변수와 DB 설정의 경계.**
배포하면 고정인 값(접속 주소·키)은 환경변수, 운영 중 화면에서 바꾸는 값(위험도·보존기간·
탐지규칙·카메라)은 DB 입니다. 섞으면 "재시작해야 반영되는 값"이 생겨 현장에서 혼란이 생깁니다.

## 이벤트 조회

필터는 **날짜 · 카메라 · 검색** 셋입니다. 분류 기준이 정해지면 항목을 늘립니다.

## 왜 MJPEG 인가

카메라 2대, 동시 시청자 1~2명 규모입니다. WebRTC(WHEP)는 지연이 짧지만 시그널링 서버·STUN·
미디어 서버가 붙어 운영 요소가 늘어납니다. MJPEG 은 `<img src>` 하나로 끝나고 프록시·방화벽을
타지 않으며, JPEG 인코딩도 카메라당 1회만 하고 시청자들이 공유합니다.

대역폭은 1280px·품질 75 기준 스트림당 약 6~12Mbps 입니다. LAN 에서 2대 × 2명이면 여유가 있습니다.

> 주의: MJPEG 은 연결을 계속 붙잡습니다. 브라우저의 동시 연결 한도(HTTP/1.1 기준 6개) 때문에
> 한 화면에 스트림을 6개 이상 띄우면 나머지 API 호출이 막힙니다. **카메라가 늘어나면** 화면당
> 동시 재생 수를 제한하거나 전송 방식을 다시 검토해야 합니다.

## 개발

```bash
# 서버 (Windows 로컬)
cd server
```

## 알아 둘 제약

- **DB 포트(11882)가 열려 있습니다.** 분석 도구로 붙기 위해서인데, 그만큼
  `POSTGRES_PASSWORD` 를 기본값으로 두면 안 됩니다.
- **인증이 없습니다.** 폐쇄망 전제입니다. 외부에서 닿는 망에 올린다면 관리자 화면(`/api/admin*`,
  `/api/cameras` 쓰기)부터 보호해야 하고, mosquitto 의 `allow_anonymous` 도 꺼야 합니다.
- **스키마는 Alembic 마이그레이션으로 관리합니다.** 서버가 기동할 때 `upgrade head` 를 자동으로
  돌립니다. 모델을 고쳤으면 마이그레이션을 함께 만들어야 합니다.
  ```bash
  cd server
  DATABASE_URL="postgresql+asyncpg://aivision:...@localhost:11882/aivision"     PYTHONPATH=. .venv/Scripts/python -m alembic revision --autogenerate -m "what changed"
  ```
  주의 두 가지 — (1) autogenerate 는 PostgreSQL 전용 표현(`now()`)을 박아 넣습니다.
  개발용 SQLite 에서도 돌아야 하니 `sa.func.now()` 로 바꾸세요. (2) 데이터가 있는 테이블에
  NOT NULL 컬럼을 추가할 때는 `server_default` 를 반드시 지정하세요.
- **서버사이드 YOLO 는 껍데기입니다.** `detection/yolo_source.py` 에 자리와 계약만 있고 추론부는
  비어 있습니다.
- **바운딩 박스는 아직 그려지지 않습니다.** 현재 ONVIF 페이로드에 좌표가 없기 때문입니다.
  화면·DB·API 는 좌표가 들어오는 순간 바로 동작하도록 준비돼 있습니다. 좌표를 얻으려면
  카메라 앱의 페이로드 계약을 확장하거나 서버 YOLO 를 구현해야 합니다.
- **카메라를 삭제하면 그 카메라의 이벤트 이력도 함께 지워집니다.** 이력을 남기려면 삭제 대신
  '사용 안 함'으로 바꾸십시오.
