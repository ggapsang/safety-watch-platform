# AI Vision 통합관제 플랫폼

**정부과제(산업부·스마트제조혁신 등)에서 반복되는 'AI 비전 기반 안전관리 솔루션' 요구를
매번 처음부터 만들지 않기 위한 틀입니다.** 판독 모델(모듈)을 갈아 끼워 제품 형태로 감싸는
것이 목표이고, 이번 현장 하나를 잘 만드는 것보다 **다음 과제에서 모듈만 바꿔 다시 쓰는 것**이
우선합니다. 그래서 특화보다 일반성을 먼저 봅니다.

VMS 의 일부 기능을 갖습니다. 영상을 받기만 하는 것이 아니라 내보내고, 녹화하고, 내보낸
영상을 모듈이 판독한 결과를 다시 받아들이고, 그 결과를 이벤트로 쌓아 화면과 외부 시스템으로
흘려보냅니다.

```
                 +---------------------- 표현 / 외부 시스템 ---------------------+
                 |  웹 대시보드          외부 관제           상위 시스템         |
                 +----- REST/WS ----------- MQTT/웹훅 ---------- REST -----------+
                                            |
 =================================== 플랫폼 코어 (버스) ==========================
   장치 레지스트리      미디어 파이프       분석 오케스트레이터     이벤트 파이프
   카메라·모듈·자격증명  수집·배포·녹화·재생  등록·할당·상태감시      정규화·승격·적재·통보
   ------------------- 통합 허브 (인바운드 바인딩 / 아웃바운드 어댑터) ------------
 ================================================================================
                                            |
   입력 어댑터           분석 모듈            출력 어댑터        미디어 서버
   RTSP·ONVIF·MQTT·HTTP  카메라 엣지·사이드카  MQTT 발행·웹훅     MediaMTX
                         ·원격·내장 룰        ·알림·PLC          fan-out·녹화·재생
```

## 매니페스토

**바꾸기 전까지, 이 넷을 어기는 설계는 반려합니다.**

**1. 코어는 버스다. 나머지는 어댑터다.**
코어는 영상을 나르고, 신호를 정규화해 쌓고, 소비자에게 흘려보냅니다. 그 이상을 하지 않습니다.

**2. 코어는 '무엇을 탐지하는가'를 모른다.**
불이 났는지, 보호구를 안 찼는지, AMR 이 뭔지 코어는 모릅니다. 코어에게는 정규화된 신호
하나일 뿐입니다.

**3. 어떤 이벤트가 들어오든 코어를 고치지 않는다.**
앞의 둘이 지켜지면 새 탐지 항목이 생기든 새 소스가 붙든 코어 코드는 그대로입니다.
바뀌는 것은 어댑터(바인딩·모듈)와 설정뿐입니다. *특정 탐지 항목에 유리하게 코어를 굽히는
결정은 그 자체로 경계 대상입니다.*

**4. 우리 네임스페이스는 특권이 아니라 편의다.**
`aivision/...` 토픽 규약은 기본 바인딩을 미리 채워 주는 편의일 뿐, 그 경로로 왔다고 특별
대우받지 않습니다. **모든 인바운드는 예외 없이 바인딩 층을 지납니다.** 이것을 어기면
플랫폼이 아닙니다.

이 원칙이 코드에서 어떻게 지켜지는지는 [설계상 지켜야 할 경계](#설계상-지켜야-할-경계)에
적어 두었습니다.

## 빠른 시작

```bash
cd aivision/deploy
cp .env.example .env
# SECRET_KEY 생성 후 .env 에 붙여 넣습니다 (카메라 비밀번호 암호화 키)
python -c "from cryptography.fernet import Fernet;print(Fernet.generate_key().decode())"

docker compose up -d --build
```

브라우저에서 `http://localhost:11880` 을 엽니다. 처음에는 카메라가 없으므로
**관리자 → 카메라 등록**에서 현장 카메라의 IP 를 등록합니다.

| 항목 | 주소 | 비고 |
|---|---|---|
| 대시보드 | `http://<서버IP>:11880` | |
| API 문서 | `http://<서버IP>:11880/api/docs` | |
| MQTT (카메라 → 서버) | `<서버IP>:1883` | 카메라의 MQTT 발행 대상(표준 포트) |
| MQTT WebSocket (브라우저) | `<서버IP>:11881` | 'MQTT 로그' 화면 직결 구독 |
| PostgreSQL | `<서버IP>:11882` | 분석·점검용 직접 조회 |
| **RTSP (분석 모듈)** | `rtsp://<서버IP>:8554/cam/{id}` | 모듈이 영상을 가져가는 곳 |
| 서버 YOLO 모듈 화면 | `<서버IP>:11990` | 학습·모델 관리. 플랫폼 탭에서도 열립니다 |
| 미디어 WebRTC / HLS | `<서버IP>:11884` / `:11885` | 브라우저 저지연 재생(현재 미사용) |

> 8080·5432 는 다른 프로그램과 자주 부딪혀 118xx 대역으로 옮겼습니다.
> **MQTT TCP 만 표준 1883 을 그대로 씁니다** — 카메라 기본값이라 여기를 옮기면 현장
> 카메라마다 설정을 바꿔야 하기 때문입니다.
> 컨테이너 안쪽은 어느 쪽이든 표준 포트라, 서버는 여전히 `base-broker:1883` · `base-db:5432`
> 로 붙습니다.
>
> 이 PC 에 Mosquitto 를 따로 설치한 적이 있다면 1883 을 이미 점유하고 있을 수 있습니다.
> `netstat -ano | findstr :1883` 으로 확인하고, 있다면 그 서비스를 먼저 내려야 합니다.

> 주의: 다른 PC 에서 접속시킬 계획이라면 `deploy/.env` 의 `MQTT_WS_URL` 을 `ws://localhost:11881` 이 아니라
> **서버 PC 의 IP** 로 바꿔야 합니다. 'MQTT 로그' 화면은 브라우저가 브로커에 직접 붙습니다.

## 컨테이너 구성

서비스 이름은 **없으면 플랫폼이 안 도는 것**과 **있어도 되고 없어도 되는 것**으로 가릅니다.
`docker compose ps` 목록만 보고도 무엇을 꺼도 되는지 알 수 있어야 하기 때문입니다.
이 경계는 compose profile 의 경계와 정확히 같습니다.

| 서비스 | 무엇 | 왜 필요한가 |
|---|---|---|
| `base-app` | FastAPI 서버 + 빌드된 화면 | 플랫폼 코어. 버스이자 API 이고, 웹 화면도 이 이미지 안에 들어 있습니다 |
| `base-db` | PostgreSQL | 카메라·바인딩·이벤트·설정. 유일한 진실의 원천 |
| `base-broker` | mosquitto | 카메라와 모듈이 판정을 실어 보내는 전선 |
| `base-media` | MediaMTX | 카메라에서 한 번만 당겨 여러 소비자에게 나눠 줍니다(fan-out) + 녹화·재생 |
| `mod-camera-meta` | 카메라 메타데이터 모듈 | 카메라가 이미 만든 박스를 읽어 화면에 그립니다 (`--profile meta`) |
| `mod-yolo` | 서버 YOLO 모듈 | 우리가 직접 학습하고 추론합니다. 자기 화면을 11990 에 띄웁니다 (`--profile yolo`) |

```bash
docker compose up -d --build                              # base-* 만
docker compose --profile meta up -d --build               # 메타데이터 모듈까지
docker compose --profile meta --profile yolo up -d --build   # 전부
```

**모듈이 별도 컨테이너인 이유**는 매니페스토 1번입니다. 코어 안에 두면 우리 모듈만 계약을
우회하는 특별 통로가 생깁니다. 밖에 두면 협력사 모듈과 완전히 같은 조건으로 붙습니다.
현실적인 이유도 있습니다 — onnxruntime·opencv 가 서버 이미지를 수백 MB(GPU 면 몇 GB) 불리고,
추론이 죽을 때 웹서버가 같이 죽어서는 안 되며, 모델 로딩이 서버 기동을 붙잡아서도 안 됩니다.

> **코드를 고쳤으면 `--build` 를 붙여야 합니다.** 화면은 빌드 결과가 서버 이미지 안에
> 구워져 들어가므로, `up -d` 만 하면 예전 이미지를 그대로 다시 띄웁니다.

서비스 이름은 컨테이너 내부 DNS 이기도 합니다(`http://base-app:8000`, `base-broker:1883`,
`base-media:8554`). 반면 **볼륨 이름은 서비스 이름을 따라가지 않습니다** — 볼륨은 이름으로
찾으므로 바꾸는 순간 새 빈 볼륨이 생기고 DB·녹화가 통째로 사라집니다.

| 볼륨 | 내용 | 누가 씁니까 |
|---|---|---|
| `db-data` | PostgreSQL 데이터 | `base-db` |
| `recordings` | 상시 녹화 세그먼트 (회전 삭제됨) | `base-media` 가 쓰고, `base-app` 이 용량을 재고 지웁니다 |
| `media-data` | 스냅샷과 이벤트 클립 (오래 보관) | `base-app` |
| `mqtt-data` · `mqtt-log` | 브로커 세션·로그 | `base-broker` |

## 카메라 등록

필요한 것은 **IP 하나**입니다. 계정·비밀번호는 카메라가 인증을 요구할 때 넣고,
포트와 스트림 경로는 기본값(554, `/profile2/media.smp`)을 그대로 쓰면 됩니다.
이름과 설치 위치를 비워 두면 IP 로 채웁니다.

**연결 테스트** 버튼은 실제로 RTSP 를 열어 첫 프레임을 받아 보고 해상도를 알려 줍니다.

비밀번호는 `SECRET_KEY` 로 암호화해 저장하며 API 응답에 실리지 않습니다.

## 미디어 평면 — fan-out · 녹화

카메라 펌웨어는 동시 RTSP 세션을 보통 5~10 개로 제한합니다. 대시보드 2명 + 분석 모듈 2개 +
녹화면 이미 한계입니다. 그래서 **카메라에서는 한 번만 당기고** 나머지는 전부 미디어 서버에서
가져갑니다.

```
[카메라] --RTSP 1개 세션--> [MediaMTX] --+--> 서버 워커 (스냅샷 · MJPEG)
                                        +--> 분석 모듈 (RTSP)
                                        +--> 디스크 (녹화)
```

분석 모듈이 영상을 가져갈 주소는 카메라 목록 API 의 `rtsp_url` 로 내려갑니다
(`rtsp://<서버>:8554/cam/{id}`).

미디어 서버 자신도 어댑터입니다. 코어는 `MediaBackend` 만 알고 MediaMTX 는 그 구현 하나입니다
(`MEDIA_BACKEND=direct` 로 바꾸면 미디어 서버 없이 카메라에 직접 붙습니다 — fan-out·녹화 없음).
미디어 서버가 죽으면 자동으로 카메라 직접 접속으로 되돌아갑니다.

### 추론용 저화질 스트림

추론 모듈이 4K 를 디코딩할 이유가 없습니다. 모델 입력은 어차피 640 으로 줄여 넣으므로
3840x2160 을 풀어 놓고 다시 줄이는 것은 CPU 를 그냥 버리는 것입니다.

카메라 설정에 **저화질 스트림 경로**를 적어 두면 미디어 서버에 보조 경로
(`cam/{id}/sub`)를 하나 더 만들어 모듈에게 줍니다. 카메라 세션이 하나 늘어나는 대신
서버 디코딩 부담이 크게 줍니다. 비워 두면 만들지 않습니다.

| | 주 스트림 | 보조 스트림 |
|---|---|---|
| 경로 | `cam/{id}` | `cam/{id}/sub` |
| 연결 | 항상 (녹화·감시 때문에) | on-demand — 보는 모듈이 없으면 끊습니다 |
| 쓰는 곳 | 화면·녹화·클립 | 추론 모듈 |

한화비전은 기종에 따라 프로파일 구성이 다릅니다. 관리자 → 카메라에서 경로를 넣기 전에
어떤 프로파일이 저화질인지 확인하십시오 — 실측한 PNV-A9082RZ 는 `profile3` 이 4K HEVC 이고
`profile10`(MOBILE)이 320x240 이었습니다. 번호만 보고 짐작하면 4K 를 하나 더 여는 셈이 됩니다.

> 320x240 은 작은 물체를 놓칠 수 있습니다. 카메라에서 중간 해상도 프로파일(예: 1280x720)을
> 하나 만들어 두는 편이 낫고, 그게 어려우면 모듈 설정에서 `PREFER_SUB_STREAM=false` 로
> 원본을 쓰게 할 수 있습니다.

### 녹화 켜고 끄기와 용량 제한

**카메라 현황** 표의 '녹화' 열에서 카메라마다 바로 켜고 끕니다. 보존 시간처럼 한 번 정하고
두는 값은 관리자 → 카메라 설정에 있습니다.

용량은 **전체 상한 하나**로 관리합니다(관리자 → 운영 설정). 디스크가 하나이므로 카메라별로
나누면 합이 디스크를 넘을 수 있어 정작 막고 싶었던 사고를 막지 못합니다. 상한을 넘으면
**가장 오래된 세그먼트부터** 지웁니다. 단 가장 최근 파일 한 건은 남깁니다 — 미디어 서버가
지금 쓰고 있을 수 있고, 열려 있는 파일을 지우면 녹화가 깨집니다.

| 제한 | 단위 | 누가 지키나 |
|---|---|---|
| 보존 시간 | 카메라별 시간 | 미디어 서버 (`recordDeleteAfter`) |
| 전체 용량 | GB | **코어** — 미디어 서버는 용량 기반 삭제를 못 합니다 |

**저장 위치**는 배포 설정입니다. `deploy/.env` 의 `RECORD_PATH` 에 도커 볼륨
이름(`recordings`, 기본)이나 호스트 폴더 경로(`D:/aivision-녹화`)를 적고
`docker compose up -d` 로 컨테이너를 다시 만듭니다. 화면에서 바꾸지 못하게 둔 이유는
컨테이너가 도는 중에 붙어 있는 디스크를 갈아 끼울 수 없기 때문입니다. 옮겨도 기존
녹화는 따라가지 않으므로 필요하면 파일을 직접 옮기십시오. 지금 어디에 쌓이는지는
관리자 → 운영 설정에 표시됩니다.

관리자 화면에 현재 사용량·파일 수·디스크 여유가 함께 뜨고, '지금 정리' 로 주기 작업(5분)을
기다리지 않고 실행할 수 있습니다.

### 녹화 책임 분리

| 관심사 | 책임 |
|---|---|
| 세그먼트 파일 쓰기 · 회전 삭제 · 구간 재생 | 미디어 서버 |
| 무엇을 언제 녹화할지 (카메라별 on/off · 보존일수) | 코어 |
| 이벤트 클립 추출과 소유 | 코어 |

**이벤트 클립은 별도 파일로 복사해 옵니다.** 세그먼트에 참조만 걸어 두면 보존기간이 지나
회전 삭제될 때 사고 영상이 같이 사라집니다. 상시 녹화는 며칠, 사고 클립은 길게 — 보존 정책이
다르기 때문입니다.

- 이벤트 발생 시 스냅샷과 **영상 클립**(전후 10초) 자동 보관
- **인바운드 바인딩** — 어떤 토픽·페이로드든 코드 없이 이벤트로 변환 (MQTT · HTTP)
- **아웃바운드** — 이벤트를 MQTT 로 내보냄. 수신 측이 죽어도 잃지 않고 재시도
- **분석 모듈 레지스트리** — 등록 · 카메라 할당 · 일감 수령 · heartbeat
- **서버 YOLO 사이드카** — 별도 컨테이너로 도는 모듈 (모델 없이 dry-run 가능)
- **카메라 메타데이터 모듈** — 카메라가 이미 만든 박스를 읽어 화면에 그림 (모델 불필요)
- **라이브 박스 오버레이** — 영상 위에 실시간 박스 (이벤트로는 쌓지 않음)
- **모듈 SDK** — 등록·일감 폴링·발행·워커 수명주기·전이 판정을 공용으로 뽑아 두 모듈이
  같이 씁니다. 모듈이 구현할 것은 `Source` 하나입니다
- MQTT 원문 수신 ('MQTT 로그' 화면), 이벤트 적재·조회, CSV 내려받기

아직 비어 있는 것:

- **탐지 항목(무엇을 이벤트로 볼지)** — 정해지지 않아 기본값을 심지 않았습니다.
  그럴듯한 항목을 미리 넣어 두면 현장과 맞지 않는 것을 나중에 지우는 일부터 해야 합니다.
- **심각도·처리 상태** — 같은 이유로 넣지 않았습니다. 컬럼도 만들지 않았습니다.
- **통계 화면** — 조회 조건과 골격만 있고 지표는 비어 있습니다. 서버의 `/api/stats` 는
  시계열·카메라별 집계를 이미 내려주므로 지표가 정해지면 붙이기만 하면 됩니다.
- **탐지 모델** — 사이드카의 배관은 다 돌지만 모델 파일이 아직 없습니다. 무엇을 판독할지
  정해지면 `.onnx` 를 `aivision/models/` 에 넣고 `CLASS_MAP` 만 채우면 됩니다.
- **아웃바운드의 다른 종류** — 웹훅 · 알림 · PLC. `kind` 를 늘리고 sender 함수를 추가하면
  붙습니다(코어는 고치지 않습니다).
- **인증** — 지금은 없습니다. 폐쇄망을 전제로 한 상태이므로, 닿을 수 있는 망에 올리기
  전에 관리자·바인딩·아웃바운드 API 를 반드시 막아야 합니다.

## 이벤트를 밖으로 내보낼 때 — 아웃바운드

관리자 → **아웃바운드** 에서 대상을 등록합니다. 지금은 MQTT 발행만 지원합니다.

| 설정 | 내용 |
|---|---|
| 조건 | 어떤 탐지 항목·카메라의 이벤트를 보낼지. 비우면 전부 |
| 토픽 | 중괄호로 값을 채웁니다. 예: `plant1/alarm/{camera.id}` |
| 페이로드 | 상대가 원하는 JSON 모양. `{event.code}` `{camera.location}` `{boxes_json}` 등 |
| | 값에 따옴표가 들어 있어도 JSON 이 깨지지 않게 자동으로 이스케이프합니다 |
| 실패 정책 | 최대 시도와 재시도 간격(실패할수록 두 배씩, 최대 5분) |

**핵심은 발송이 아니라 실패 처리입니다.** 수신 측이 죽어 있어도 발송 대기가 DB 에 남아
**서버를 재시작해도 이어서 보냅니다.** 최대 시도를 넘기면 포기하고 사유를 남깁니다.
'전달 이력' 화면에서 시도 횟수와 실패 사유를 확인할 수 있습니다.

## 쏟아질 때 막는 두 층

같은 신호가 초당 수백 번 들어와도 견뎌야 합니다. 층을 둘로 나눴습니다 — 막는 이유가
다르고, 값도 다르기 때문입니다.

| | 완충장치 | 중복 억제 |
|---|---|---|
| 무엇을 같다고 보나 | **같은 메시지** (토픽 + 페이로드가 글자 그대로 동일) | **같은 상황** (같은 카메라 · 같은 탐지 항목) |
| 판단 | 메모리 | DB 조회 |
| 기본 간격 | 1초 | 20초 |
| 걸리면 | 바인딩도 DB 도 타지 않고 버립니다 | 이벤트로 승격하지 않습니다 |
| 어디서 | 문 앞 (MQTT·HTTP 공통) | 이벤트 승격 |

완충장치를 앞에 둔 이유는 값입니다. 중복 억제만 있으면 메시지 하나마다 바인딩 평가와
DB 왕복이 붙어, 막아 주는 그 일이 곧 부하가 됩니다. 문 앞에서 지문만 비교해 버리면
그 비용이 들지 않습니다.

**(토픽 + 페이로드)로 묶는 이유**는 '같은 메시지'를 글자 그대로 해석하기 위해서입니다.
그래야 내용이 매번 달라지는 라이브 박스는 건드리지 않고(좌표가 매번 다릅니다), 빈
페이로드 연발과 고정 문구 알람만 정확히 걸립니다. 간격은 관리자 → 운영 설정에서 바꾸고
0 으로 두면 끕니다.

> 큐에 쌓았다가 나중에 처리하지 않고 버립니다. 같은 메시지라 나중에 처리해도 결과가
> 같고, 쌓아 두면 폭주할 때 메모리가 대신 터집니다.

**빈도가 아니라 내용으로 걸러야 할 때**는 바인딩의 페이로드 조건을 씁니다. 예를 들어
`{"$._raw": "someone invasion"}` 을 걸어 두면 빈 메시지는 아예 이벤트가 되지 않습니다.
완충장치는 '얼마나 자주'를, 페이로드 조건은 '무엇을' 막습니다.

### 수신 원문은 기본적으로 DB 에 남기지 않습니다

관리자 → 운영 설정에서 켭니다. 기본이 끔인 이유는 두 가지입니다. 라이브 박스처럼 초당
여러 번 들어오는 트래픽을 적재하면 카메라 두 대만으로 하루 수십만 줄이 쌓이고, 정작
원문 로그를 둔 이유(사후에 되짚기)도 그 잡음에 묻힙니다.

**꺼 두어도 '모르는 토픽 찾기'는 막히지 않습니다.** 'MQTT 로그' 화면은 브로커에 직결
구독하므로 실시간으로 무엇이 오는지 보는 데 DB 가 필요 없습니다.

| 설정 | 뜻 |
|---|---|
| 남기지 않음 | 기본 |
| 바인딩에 안 걸린 것만 | 새 소스를 붙이는 동안 쓰기 좋습니다 |
| 전부 | 짧게 켰다 끄세요 |
| 지정 채널만 | 토픽 패턴을 채우면 위 선택보다 우선합니다 (`+/fireAlarm, vendorX/#`) |

> 주의: 여기서 발행한 토픽에 **인바운드 바인딩을 만들지 마세요.** 서버는 모든 토픽을
> 구독하므로, 내보낸 것을 다시 받아 이벤트로 만들면 무한히 늘어납니다.

## 분석 모듈을 붙일 때

코어는 모듈이 **어디서 도는지 모릅니다.** 서버 프로세스 안이든 옆 컨테이너든 다른 PC 든
카메라 안이든, 결과만 같은 문으로 들어오면 됩니다.

모듈이 하는 일은 셋뿐입니다.

```bash
# 1. 등록 (같은 id 로 다시 부르면 갱신 — 재시작할 때마다 실패하면 곤란하다)
curl -X POST localhost:11880/api/modules -H 'Content-Type: application/json'   -d '{"id":"yolo-ppe","name":"PPE 판독","kind":"sidecar","capabilities":["ITEM-001"]}'

# 2. 무엇을 볼지 물어본다 -> 카메라별 RTSP 주소와 옵션을 받아 간다
curl localhost:11880/api/modules/yolo-ppe/work
#  {"items":[{"camera_id":4,"rtsp":"rtsp://base-media:8554/cam/4","options":{"min_conf":0.5}}]}

# 3. 판정 결과를 보낸다 — MQTT 발행 또는 HTTP
curl -X POST localhost:11880/api/ingest -H 'Content-Type: application/json'   -d '{"topic":"aivision/detect/4/yolo-ppe","payload":{"camera_id":4,"item":"ITEM-001",
       "confidence":0.88,"boxes":[{"x1":0.1,"y1":0.2,"x2":0.3,"y2":0.6}]}}'
```

카메라 할당은 관리자가 정합니다(`POST /api/modules/{id}/assignments`). 옵션(ROI·스케줄·
임계값)은 JSON 이고 **코어는 그 내용을 해석하지 않습니다** — 모듈에 그대로 넘깁니다.
코어가 탐지 파라미터를 이해하기 시작하면 매니페스토 2번이 깨집니다.

모듈에는 **카메라 IP 나 계정을 주지 않습니다.** 미디어 서버 주소만 주므로 카메라 부하도
늘지 않습니다.

### 라이브 박스와 이벤트는 다른 길로 갑니다

| | 이벤트 | 라이브 박스 |
|---|---|---|
| 빈도 | 가끔 | 초당 여러 번 |
| 영속 | 한다 (스냅샷·클립 첨부) | 안 한다 |
| 경로 | 바인딩 -> 승격 -> DB -> WebSocket | 바인딩 -> WebSocket (통과만) |

바인딩에서 **라이브 전용**을 켜면 같은 매핑 문법을 쓰면서 적재를 건너뜁니다.
초당 수십 건을 이벤트 파이프에 태우면 DB 가 감당하지 못합니다.

## 카메라가 만든 박스 그리기 — 메타데이터 모듈

`aivision/modules/onvif_meta/`. **우리가 추론하지 않습니다.** 한화비전 카메라는 RTSP 에
데이터 트랙을 하나 더 실어 보내고, 그 안에 카메라 안에서 돌고 있는 분석(WiseAI 등)이 만든
`tt:BoundingBox` 와 클래스·신뢰도가 들어 있습니다. 그것을 읽어 화면에 그리기만 합니다.

```bash
cd aivision/deploy
docker compose --profile meta up -d --build mod-camera-meta
docker compose logs -f mod-camera-meta
```

띄운 뒤 관리자에서 **모듈에 카메라를 할당**하고, 프리셋 '우리 모듈 (라이브 박스)' 로
바인딩을 하나 만들면 끝입니다.

**이 모듈은 이벤트를 만들지 않습니다.** `aivision/live/{camera_id}` 만 발행합니다.
사람이 서 있는 동안 초당 여러 번 나오는 판독을 이벤트로 쌓으면 DB 가 무너지고, 그것은
'라이브 박스는 이벤트가 아니다'라는 원칙을 정면으로 어깁니다. 무엇을 이벤트로 볼지는
따로 정합니다(예: 지정 구역에 일정 시간 이상 머무름) — 그때는 그 판단을 하는 모듈이
`aivision/detect/...` 로 발행하면 되고 이 모듈은 그대로 둡니다.

좌표는 프레임이 알려 주는 `tt:Transformation` 으로 정규화합니다. 해상도를 설정으로 받지
않는 이유가 이것입니다 — 스트림 프로파일이 바뀌어도 프레임이 스스로 기준을 들고 옵니다.
기준을 알 수 없는 프레임은 **그리지 않습니다.** 틀린 자리에 그리는 것보다 낫습니다.

| 설정(.env) | 뜻 |
|---|---|
| `META_CLASS_MAP` | 카메라 클래스 이름 -> 화면에 쓸 이름. 예 `{"Human":"사람"}`. 비우면 원래 이름 |
| `META_KEEP_UNMAPPED` | 표에 없는 클래스도 그릴지 (기본 켬 — 무엇이 잡히는지 보려고) |
| `META_SKIP_CLASSES` | 그리지 않을 클래스. 기본 `Head,Face` — 사람 하나에 Human·Head·Face 가 겹쳐 나와 박스가 세 겹이 됩니다 |
| `META_LIVE_MIN_INTERVAL` | 라이브 발행 최소 간격(초). 기본 0.2 |

```bash
cd aivision/modules/onvif_meta && python tests.py    # 카메라 없이 파서 검증
```

## 서버 YOLO 모듈 — 학습부터 추론까지

`aivision/modules/yolo/` 에 있습니다. **코어 코드가 아니라 모듈 계약의 사용자**입니다.
다른 모듈과 다른 점이 둘 있습니다 — **학습까지 여기서 돌리고**, 그래서 **자기 화면을
직접 띄웁니다**(기본 11990).

코어에 넣지 않은 이유가 셋입니다. torch·onnxruntime·opencv 가 서버 이미지를 GB 단위로
불립니다. 학습이나 추론이 죽을 때 웹서버가 같이 죽습니다. 모델 로딩이 서버 기동을 붙잡습니다.
그리고 넷째가 가장 중요합니다 — 코어 안에 두면 우리 모듈만 계약을 우회하는 특별 통로가
생깁니다. 별도 컨테이너로 두면 협력사 모듈과 완전히 같은 조건으로 붙습니다.

```bash
cd aivision/deploy
docker compose --profile yolo up -d --build      # 기본은 꺼져 있습니다
docker compose logs -f mod-yolo
```

### 화면은 모듈이 띄우고, 플랫폼은 탭으로 감쌉니다

이 모듈은 사람이 할 일이 있습니다 — 데이터셋을 고르고, 학습을 돌리고, 로그를 지켜보고,
어느 가중치를 쓸지 정합니다. 그 화면을 플랫폼에 넣으면 **코어가 YOLO 를 알게 됩니다**
(매니페스토 2번). 그래서 화면도 모듈이 가집니다.

플랫폼은 모듈이 등록할 때 준 `endpoint` 를 사이드바 **모듈** 그룹에 탭으로 만들고 iframe
으로 감싸기만 합니다. 코어 코드에는 'yolo' 라는 단어가 한 번도 나오지 않습니다 — 협력사가
자기 화면을 들고 와도 똑같이 동작합니다.

브라우저가 닿는 주소여야 하므로 다른 PC 에서 접속시킬 계획이면 `.env` 의
`YOLO_PUBLIC_URL` 을 서버 PC 의 IP 로 바꿔야 합니다.

### 학습

학습은 **자식 프로세스**로 돌립니다. 몇 시간을 돌고 죽을 때 프로세스를 통째로 데려가므로
(CUDA OOM, segfault) 같이 두면 추론과 화면이 함께 죽습니다. 한 번에 하나만 돌립니다 —
GPU 가 하나여서 둘을 돌리면 둘 다 느려지거나 OOM 이 납니다.

| 준비할 것 | 어디에 |
|---|---|
| 데이터셋 (이미지·라벨 + yaml) | `training` 볼륨의 `/training/datasets` |
| 사전학습 가중치 `yolov7_training.pt` | `aivision/models/` ([공식 릴리스](https://github.com/WongKinYiu/yolov7/releases)) |

**라벨링과 데이터 준비는 이 모듈의 일이 아닙니다.** 준비된 데이터셋 yaml 을 가리키기만
합니다. 학습이 끝나면 화면에서 '모델로 쓰기' 를 누르면 ONNX 로 내보내
`aivision/models/` 에 복사합니다. 학습 폴더를 지워도 쓰던 모델이 사라지지 않도록
참조가 아니라 **복사**합니다.

```bash
# 학습에는 CUDA 판 torch 가 필요합니다. 기본 이미지는 CPU 판이라 어디서든 빌드만 됩니다.
docker compose build --build-arg TORCH_INDEX=https://download.pytorch.org/whl/cu121 mod-yolo
# 그리고 docker-compose.yml 의 mod-yolo deploy 블록(GPU 예약) 주석을 풉니다.
```

학습 본체는 `modules/yolo/vendor/yolov7/` 입니다. 원본
([WongKinYiu/yolov7](https://github.com/WongKinYiu/yolov7), **GPL-3.0**)에서 학습·평가·
내보내기에 필요한 27개 파일만 옮겼습니다. 자세한 것은 `vendor/README.md` 를 보십시오.

띄운 뒤 해야 하는 일은 둘입니다. 관리자 화면에서 **모듈에 카메라를 할당**하고,
**인바운드 바인딩**을 만드는 것입니다(프리셋 '우리 모듈 (탐지)' · '우리 모듈 (라이브 박스)'
버튼이 폼을 채워 줍니다). 바인딩이 없으면 발행은 되지만 이벤트가 되지 않습니다 —
우리 모듈에도 특권이 없기 때문입니다.

| 설정(.env) | 뜻 |
|---|---|
| `YOLO_MODEL_PATH` | 컨테이너 안 모델 경로. 기본 `/models/best.onnx` (`aivision/models/` 가 마운트됩니다) |
| `YOLO_CLASS_MAP` | 모델 클래스 -> 탐지 항목 코드. 예 `{"no_helmet":"ITEM-001"}`. **모델이 바뀌면 이것만 바꿉니다** |
| `YOLO_DEVICE` | `cpu` 또는 `cuda` (CUDA 를 못 쓰면 CPU 로 자동 폴백합니다) |
| `YOLO_SAMPLE_FPS` | 초당 몇 장만 볼지. 기본 3 |
| `YOLO_HOLD_SEC` | 이 시간 동안 안 보이면 해제로 봅니다. 기본 3초 |
| `YOLO_MIN_CONF` | 이벤트로 올릴 최소 신뢰도. 기본 0.4 |
| `YOLO_LAYOUT` | 출력 텐서 해석. 기본 `auto`, 틀리면 `v5` / `v8` / `nms` 로 못 박습니다 |
| `YOLO_DRY_RUN` | 모델 없이 합성 박스를 발행 |

`CLASS_MAP` 에 없는 클래스는 무시합니다. 모델이 80 클래스를 알더라도 이 현장이 관심 있는
것만 이벤트가 됩니다. 항목 코드는 **플랫폼에 먼저 만들어 둔 탐지 항목**이어야 합니다 —
없는 코드로 발행하면 바인딩이 "탐지 항목이 등록되어 있지 않음" 으로 떨굽니다.

### 모델이 없어도 전 경로를 확인할 수 있습니다

`YOLO_DRY_RUN=true` 로 두면 영상도 모델도 없이 합성 박스를 주기적으로 발행합니다
(15초 발생 · 10초 해제 반복). 등록 -> 일감 -> 발행 -> 바인딩 -> 이벤트 -> 스냅샷·클립 ->
라이브 오버레이가 전부 도는지 눈으로 볼 수 있습니다. 모델이 지정돼 있어도 파일이 없으면
같은 모드로 내려앉습니다 — 컨테이너가 재시작을 반복하는 것보다 낫습니다.

모델이 오면 갈아 끼우는 곳은 `inference.py` 뿐이고, 배관(`main.py`)과 전이 판정
(SDK 의 `debounce.py`)은 그대로입니다.

```bash
# 모듈 자체 검증 (브로커·모델·카메라 없이 돕니다)
cd aivision/modules/yolo && python tests.py
```

### 전이만 발행합니다

프레임마다 발행하면 브로커와 DB 가 무너집니다. SDK 의 `debounce.py` 가 **올라가는 순간과 내려가는
순간만** 남깁니다 — 발생은 즉시(늦추면 안전관리에서는 그게 사고입니다), 해제는 `hold_sec`
동안 한 번도 보이지 않은 뒤입니다. 한두 프레임 놓친 것으로 해제하면 화면이 깜빡입니다.

## 새 소스를 받아들일 때 — 인바운드 바인딩

무엇을 이벤트로 볼지는 코드가 아니라 **DB** 에 있습니다.
**어떤 토픽도 특권을 갖지 않습니다** — 협력사가 정한 임의 토픽도 등록하면 똑같이 동작합니다.
우리가 만든 모듈이 쓰는 토픽 모양도 예외가 아닙니다. 화면의 **프리셋**은 흔한 모양을 폼에
채워 주는 입력 도우미일 뿐이고, 만들어진 바인딩은 다른 것과 똑같은 데이터입니다.

1. **MQTT 로그** 화면에서 실제로 어떤 토픽·페이로드가 오는지 봅니다.
   바인딩에 안 걸린 메시지도 전부 보관되므로 모르는 토픽도 일단 보입니다.
2. 메시지를 눌러 **바인딩 만들기** 를 누르면 그 토픽·페이로드가 시험 화면으로 넘어갑니다.
3. `solutions` 에 탐지 항목을 넣고, 관리자 → **인바운드 바인딩** 에서 규칙을 만듭니다.
4. '시험' 으로 걸리는지 확인합니다. 안 걸리면 사유를 알려 줍니다.

전송 방식은 MQTT 와 HTTP 둘입니다. **둘 다 같은 바인딩 층을 지납니다** — 전송이 다르다고
특별 대우를 받지 않습니다. MQTT 를 못 쓰는 모듈은 `POST /api/ingest` 로 토픽과 페이로드를
그대로 밀어넣으면 됩니다.

바인딩은 두 부분입니다.

| | 내용 |
|---|---|
| 무엇이 걸리는가 | 토픽 패턴(MQTT 와일드카드) + 페이로드 조건 |
| 어떻게 뽑는가 | 카메라 · 탐지항목 · 상태 · 판정 주체 · 신뢰도 · 박스를 각각 표현식으로 |

**라이브 전용 바인딩은 탐지 항목을 요구하지 않습니다.** 탐지 항목은 '무엇을 이벤트로
볼지' 를 정하는 것인데 라이브 박스는 이벤트가 아니기 때문입니다. 요구하면 박스를 그리려고
쓰지도 않을 항목을 하나 만들어 두게 됩니다.

**판정 주체**(`module_expr`)는 '무엇이 판정했나' 입니다. 페이로드에 모듈 식별자가 실려 오면
뽑아 이벤트에 남기고, 이벤트 상세에 보여 줍니다. 비워도 됩니다 — 카메라 엣지처럼 자기를
밝히지 않는 소스가 많습니다. '어느 규칙이 걸렸나'(바인딩)와는 다른 축이라 따로 둡니다.

표현식 문법은 넷뿐입니다 — `$.a.b`(페이로드) · `$topic[2]`(토픽 조각) · `$mac` · 리터럴.
페이로드 형식으로 `onvif` 를 고르면 ONVIF 의 `SimpleItem` 배열을 평면 키로 펴 줍니다.
박스는 픽셀·정규화·중심좌표 어느 형식으로 와도 **0~1 정규화로 통일해** 저장합니다.

## 디렉터리 구성

최상위가 **코어(`server/`)와 모듈(`modules/`)로 갈라져 있는 것**이 이 저장소의 핵심입니다.
매니페스토 1번이 디렉터리에 그대로 드러납니다 — 코어는 모듈을 import 하지 않고, 모듈은
코어를 import 하지 않습니다. 둘은 오직 계약(REST + MQTT)으로만 만납니다.

```
저장소 루트
├─ aivision/          새 코드 전부
└─ refs/              참고용 (빌드에 들어가지 않습니다)
   ├─ demo/           디자인 시안
   └─ legacy-iseco-pc/  이전 PC 추론 앱 (후처리 코드를 여기서 가져왔습니다)
```


코어는 건드리지 않습니다 — 그것이 매니페스토 3번이 지켜지고 있다는 증거입니다.

### 설계상 지켜야 할 경계

**1. 탐지 소스는 갈아 끼울 수 있어야 합니다.**
판정이 카메라 엣지(MQTT)에서 오든, 서버 YOLO 사이드카에서 오든, 나중에 외부 서비스에서
오든 `DetectionSignal` 이라는 같은 모양으로 들어오고 그 뒤 처리는 완전히 동일합니다.
추론기를 붙이는 일은 소스를 추가하는 일이 아니라 **모듈을 등록하는 일**입니다 —
서버 YOLO 도 코어 밖에서 같은 문(인바운드 바인딩)을 지납니다.

**2. 영상과 박스는 다른 채널로 갑니다.**
서버는 프레임에 바운딩 박스를 굽지 않습니다. 영상은 MJPEG(`<img>`), 박스는 WebSocket JSON 으로
따로 가고 브라우저가 SVG 로 겹칩니다. 그래서 판정이 늦게 도착해도 어긋나지 않고,
나중에 전송 방식을 바꿔도 오버레이 코드는 그대로이며, 한글 라벨이 깨지지 않습니다.

**3. 박스 좌표는 0~1 정규화로만 저장합니다.**
카메라 해상도가 섞이고, 엣지 추론은 640 입력 좌표계로 뱉고, 화면은 CSS 픽셀 위에 그립니다.
픽셀로 저장하면 변환 지점이 세 군데로 흩어집니다.

**4. 환경변수와 DB 설정의 경계.**
배포하면 고정인 값(접속 주소·키)은 환경변수, 운영 중 화면에서 바꾸는 값(위험도·보존기간·
탐지규칙·카메라)은 DB 입니다. 섞으면 "재시작해야 반영되는 값"이 생겨 현장에서 혼란이 생깁니다.

## 이벤트 조회

필터는 **날짜 · 카메라 · 검색** 셋입니다. 분류 기준이 정해지면 항목을 늘립니다.

## 왜 MJPEG 인가

카메라 2대, 동시 시청자 1~2명 규모입니다. WebRTC(WHEP)는 지연이 짧지만 시그널링 서버·STUN·
미디어 서버가 붙어 운영 요소가 늘어납니다. MJPEG 은 `<img src>` 하나로 끝나고 프록시·방화벽을
타지 않으며, JPEG 인코딩도 카메라당 1회만 하고 시청자들이 공유합니다.

대역폭은 1280px·품질 75 기준 스트림당 약 6~12Mbps 입니다. LAN 에서 2대 × 2명이면 여유가 있습니다.

> 주의: MJPEG 은 연결을 계속 붙잡습니다. 브라우저의 동시 연결 한도(HTTP/1.1 기준 6개) 때문에
> 한 화면에 스트림을 6개 이상 띄우면 나머지 API 호출이 막힙니다. **카메라가 늘어나면** 화면당
> 동시 재생 수를 제한하거나 전송 방식을 다시 검토해야 합니다.

## 알아 둘 제약

- **DB 포트(11882)가 열려 있습니다.** 분석 도구로 붙기 위해서인데, 그만큼
  `POSTGRES_PASSWORD` 를 기본값으로 두면 안 됩니다.
- **인증이 없습니다.** 폐쇄망 전제입니다. 외부에서 닿는 망에 올린다면 관리자 화면(`/api/admin*`,
  `/api/cameras` 쓰기)부터 보호해야 하고, mosquitto 의 `allow_anonymous` 도 꺼야 합니다.
- **스키마는 Alembic 마이그레이션으로 관리합니다.** 서버가 기동할 때 `upgrade head` 를 자동으로
  돌립니다. 모델을 고쳤으면 마이그레이션을 함께 만들어야 합니다.
  ```bash
  cd server
  DATABASE_URL="postgresql+asyncpg://aivision:...@localhost:11882/aivision"     PYTHONPATH=. .venv/Scripts/python -m alembic revision --autogenerate -m "what changed"
  ```
  주의 두 가지 — (1) autogenerate 는 PostgreSQL 전용 표현(`now()`)을 박아 넣습니다.
  개발용 SQLite 에서도 돌아야 하니 `sa.func.now()` 로 바꾸세요. (2) 데이터가 있는 테이블에
  NOT NULL 컬럼을 추가할 때는 `server_default` 를 반드시 지정하세요.
- **모델 파일이 없으면 사이드카는 dry-run 으로 내려앉습니다.** 컨테이너를 죽여 재시작을
