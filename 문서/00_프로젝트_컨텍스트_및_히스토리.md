## 0. 30초 요약

- 컨베이어 위 **부적합(쓰레기/이물) 탐지**를 하고, 결과를 등급(0/1/2)으로 산출해 **PLC에 전달**하는 시스템이다.
- 원래는 이 추론을 **카메라 내부(온디바이스 NPU)** 에서 돌리는 제품(`daim_detector`)이었다.
- 그런데 이 사이트 모델은 카메라 NPU에 올리면 **양자화가 붕괴**해서 정상 동작하지 않는다. (confidence가 0/100으로만 튐)
- 그래서 **추론 위치를 카메라 → PC로 이관**했다. 카메라는 영상(RTSP)만 보내고, PC가 `best_trash.onnx`로 추론해서 결과를 PLC로 보낸다.
- 이 PC 앱이 지금 만드는 대상이다. **판정 로직과 PLC 통신 규격은 기존 카메라 앱에서 이미 검증된 것을 그대로 가져온다.**

## 3. 원래 방식(카메라 온디바이스)과 그 실패

### 3.1 `daim_detector`가 뭔가

- 한화 OpenSDK 위에서 **카메라 안에서 직접 도는** C++ 앱. 원래는 손 검출(`network_binary.nb`)과 쓰레기 검출(`trash_binary.nb`)을 지원.
- 카메라 NPU가 `.nb` 모델로 추론 → 후처리(NMS 등) → 결과를 카메라의 알람아웃/메타데이터/PLC로 전달.
- 이 앱에는 이미 **잘 만들어 둔 자산**이 많다(아래 9장). 특히 **판정 로직**과 **XGT PLC 통신**은 현장 검증됨 → PC 앱은 이걸 그대로 포팅.

### 3.2 양자화 붕괴 (전환의 직접 원인)

- 아이에스에코솔루션용 쓰레기 모델을 카메라 NPU용 `.nb`로 변환(ONNX → NPU toolchain → `.nb`)하면, **양자화 과정에서 모델이 무너진다.**
- 증상: confidence가 **0 또는 100으로만 극단적으로** 튄다. 정상적인 확률 분포가 안 나옴 → 사용 불가.
- 해결 가능성이 불투명하고, 시연/검수 일정은 정해져 있음 → **카메라 NPU 경로를 포기**하고 우회한다.

> 손 검출 모델(`network_binary.nb`)은 카메라에서 문제없이 돌았다. 쓰레기 모델만 이 붕괴가 발생. 모델 특성 차이로 보이며, 근본 개선(양자화 안정화)은 **별도 트랙**으로 시간을 두고 진행한다. 이 PC 앱의 범위 밖.

## 4. 전환 결정 — PC 추론

### 4.1 결정 내용

추론을 카메라에서 **PC로 옮긴다.**

```
[원래 의도 — 실패]
  모델 학습 → ONNX → NPU toolchain → .nb → 카메라 앱 → 빌드 → (양자화 붕괴 ✗)

[전환 — 채택]
  모델 학습 → ONNX
  카메라: 영상(RTSP)만 PC로 송출
  PC:     ONNX/토치 등 안정적인 라이브러리로 추론 → 결과를 PLC로 전송
  PLC ↔ 컨베이어
```

### 4.2 왜 문제가 없나

- 검수/시연 시 대시보드를 띄워 설명해야 하므로 **PC는 어차피 상시 연결**되어 있다.
- PC ↔ PLC는 이더넷으로 직접 통신하므로 PC에서 곧바로 PLC에 신호를 줄 수 있다.
- 즉 "카메라는 dumb sensor(영상 소스), 판단·제어의 두뇌는 PC"라는 구조. 산업 비전에서 흔한 엣지-PC 추론 아키텍처다.

### 4.3 아키텍처

```
카메라 ──RTSP(H.264)──▶ PC ──────────────────▶ PLC(XGT TCP 2004) ──▶ 컨베이어
                         │ OpenCV 수신
                         │ ONNX Runtime 추론
                         │ 판정(2초 window + 9매트릭스)
                         │ 대시보드(후속)
                         └ XGT write D8100/D8101
```

## 5. 모델 상세 (⚠ 구현에 직접 영향)

### 5.1 라벨 통일 트릭

- 모델은 **네 가지 물체를 각각 학습**해야 정확도가 오른다(각 물체 특징을 따로 학습). 하지만 **출력 라벨은 `trash` 하나로 통일**해야 한다.
- `best.pt`(파라미터만 있는 원본)는 라벨을 하나로 합치는 역할을 못 한다 → **코드 단에서 통일**해야 함.
- 그래서 **이미 통일 처리가 반영된** 두 파일을 받았다:
  - `best_trash.onnx`
  - `best_trash.torchscript.pt` — yolov7 레포 없이 `torch.jit.load()` 한 줄로 로드되는 완성 모델.
- **결론: 앱은 단일 클래스(`trash`)로 처리하면 된다.** 4물체 구분은 모델 내부에서 끝났고 출력은 trash 단일.

### 5.2 입출력 규격 (카메라 config 기준)

| 항목 | 값 |
|:---|:---|
| 아키텍처 | YOLOv7, `nc=1` |
| 입력 | 640×640, 입력 텐서명(카메라 .nb) `images_0` |
| 출력(카메라 .nb) | 단일 텐서 `attach_output0/out0`, shape `[1, 25200, 6]` = `[x,y,w,h,obj,cls]` **raw logit** (sigmoid/anchor decode/NMS 를 앱이 수행) |

### 5.3 ⚠ .nb 와 onnx 의 전처리/후처리 차이 (반드시 인지)

- **카메라 `.nb`**: 입력 `uint8`, 정규화를 NPU가 내부 처리(`add_preproc_node: true`) → 앱은 `/255` **하면 안 됨**. resize는 직접 stretch.
- **PC `.onnx`(표준 YOLOv7 export)**: 보통 입력 `float32`, `/255` 정규화 필요, letterbox resize 표준, 그리고 **출력이 이미 grid-decode + sigmoid 된 상태**(Detect 레이어 포함)일 가능성이 높다 → 이 경우 앱은 **conf 필터 + NMS 만** 하면 되고 anchor decode 불필요.
- **최초 통합 시 반드시 확인**: onnx 출력 shape/값을 찍어서
  - 픽셀 좌표의 디코딩된 박스(`[1,N,6]`) → `decoded` 모드
  - raw logit → `raw` 모드(카메라 anchor decode 로직 재사용)

  → 현재 코드(`detector.py`)는 첫 프레임에서 출력 shape/샘플을 자동 로그로 찍고, `infer_mode` 설정으로 두 경로를 전환하도록 되어 있다.

## 6. PLC · XGT 프로토콜 상세 (⚠ "그대로" 포팅 대상)

### 6.1 IF 맵 (mailbox 컨벤션 — daim_detector 와 동일)

| 방향 | 디바이스 | 이름 | 값/의미 |
|:---:|:---:|:---|:---|
| PLC → PC (read) | **D8000** | PLC Ready | 0/1 |
| PLC → PC (read) | **D8001** | Conveyor RUN | 0/1 |
| PC → PLC (write) | **D8100** | PC Ready | 0/1 (앱 기동/정지 신호) |
| PC → PLC (write) | **D8101** | 결과 코드 | **0=정상 / 1=부분오염 / 2=많이오염** |

- 즉 `D8000/D8001`은 PC가 읽는 입력, `D8100/D8101`은 PC가 쓰는 출력.
- LS D-영역 word 주소를 XGT에서는 `%DW8101` 형식 문자열로 지정한다.

### 6.2 XGT 전용 프로토콜 와이어 (카메라 `xgt_client.cc` 검증본)

- 포트 **2004** (XGT 전용 프로토콜 TCP).
- CPU Info: XGB 계열 접속은 **CPU_ANY(0x00)** 권장(문서 기본값).
- **프레임 = Company Header(20 byte) + Body**:
  - Company ID 10 byte: `"LSIS-XGT\x00\x00"`
  - PLC Info(LE, 2) `0x0000` / CPU Info(1) / Source(1)=`0x33`(client→server)
  - Invoke ID(LE, 2, 매 호출 증가) / Body Length(LE, 2) / Position(1)=`0x00`
  - **BCC(1)** = 헤더 앞 19바이트 합 & 0xFF
- **Body(Read/Write)**:
  - Command(BE, 2): Read=`0x5400`/Write=`0x5800` (응답 Read=`0x5500`/Write=`0x5900`)
  - Data Type(BE, 2): Word=`0x0200`
  - Reserved(LE, 2) `0x0000` / Block count(LE, 2)
  - Write: (이름길이 LE + 이름) 블록들 → (값길이 LE + 값 LE) 블록들
  - Read: (이름길이 LE + 이름) 블록들
- 응답 파싱: 헤더 20byte 수신 → body length(offset 16, LE) → body 수신 → command/err_state(offset 6, LE) 확인.
- **1회 자동 재연결(WithReconnect)**: IO 실패 시 close 후 1회 재시도. `ECONNREFUSED`는 backoff(20→200ms).

> 이 전부가 `xgt_client.py`에 그대로 포팅되어 있고, WriteWord/ReadWord 프레임 바이트를 C++ 원본과 대조 검증 완료.

## 7. 판정 로직 히스토리 (⚠ 설계 문서 그대로)

### 7.1 두 개의 정책이 있었다

`daim_detector`에는 모델별로 서로 다른 알람 정책이 있다.

| | network 정책(손 검출) | **trash 정책(이 앱이 쓰는 것)** |
|:---|:---|:---|
| 윈도우 | 1초 tumbling(5프레임) | **2초 sliding(10프레임)** |
| 집계 | 최빈값 count | **max(count) / max(area_ratio)** |
| 분류 차원 | count 단일 | **count + area_ratio 2차원** |
| 결과 | Send/Skip | **9매트릭스 → 3-level(0/1/2) 축약** |
| 발송 | MQTT | **XGT only** |

이 PC 앱은 **trash 정책**만 구현한다.

### 7.2 trash 정책 상세 (2026-06-30 설계 + 2026-07-01 개정)

1. 매 프레임: `count = 검출 수`, `area_ratio = bbox 총면적 / ROI(또는 프레임) 면적`.
2. 최근 **2초** 윈도우에서 `max_count`, `max_area_ratio`.
3. 분류:
   - **count**: `< low` → L / `>= high` → H / 그 외 M. *(2026-07-01: 상한 경계 포함 `>` → `>=`)*
   - **area**: `< low` → L / `> high` → H / 그 외 M. *(area는 경계 미포함 유지)*
   - 기본 임계값(2026-07-01 개정): count `low=1, high=2`, area `low=0.3, high=3.0`.
4. 9매트릭스 카테고리 `"L_L".."H_H"`.
5. **XGT 코드 = `max(count_level, area_level)`** → `0`(=L_L, skip) / `1`(하나라도 M) / `2`(하나라도 H).
   - *(원래 9매트릭스를 1~8로 쓰려던 설계를 07-01에 3-level로 축약. 사용자 결정.)*
6. **cooldown**(별도 `trash_cooldown_sec`, 기본 8초, 최소 1초) + **9매트릭스 카테고리 변경 시 우회**(위협 수준 변화는 즉시 발송).
7. 발송 시 `D8101`에 코드(1/2) write.

### 7.3 ⚠ L_L(정상) 처리 — 판단 필요 지점

- **설계 문서 원칙**: `L_L`은 **write를 스킵**한다 → PLC는 직전 코드를 유지.
- **컨베이어 관점의 고려**: 많이오염(2) → 정상으로 돌아왔을 때 `D8101`이 2에 latched된 채 남는다. 컨베이어를 정상 복귀시키려면 0을 명시적으로 써야 할 수 있음.
- 현재 코드는 **설계 문서 충실(스킵)이 기본**, `write_zero_on_normal=True`로 두면 정상 복귀 시 0 write.
- → **현장 PLC 로직이 D8101을 어떻게 소비하는지 확인 후 확정할 것.**

### 7.4 ⚠ fps-윈도우 이식 메모

- 카메라는 5fps라 "10프레임 = 2초"였다. PC 추론 fps는 다를 수 있어, `trash_logic.py`는 **프레임 수 고정이 아니라 '최근 2초 시간 기반'** 윈도우로 구현했다. '2초'라는 의미를 fps와 무관하게 보존하기 위함.

## 8. 기존 daim_detector 자산 — 재사용 / 미사용

### 8.1 재사용(개념/로직 포팅)

- **XGT PLC 통신** (`xgt_client.cc` → `xgt_client.py`)
- **판정 로직** (2026-06-30 설계 문서 → `trash_logic.py`): sliding window, 9매트릭스 분류, cooldown decider
- **YOLOv7 후처리** (raw 경로가 필요할 경우 anchor decode 로직 참고)
- **PLC IF 맵 / 주소 컨벤션** (D8000/8001/8100/8101)

### 8.2 미사용(PC 방식에서 불필요 → 의도적으로 제외)

- SUNAPI / IVA 영역 SUNAPI 연동 (ROI는 앱 설정값으로 대체)
- MQTT publish (이 사이트는 PLC 직접 제어가 목적)
- ONVIF 메타데이터 / 카메라 rule engine / OSD
- 이벤트 이미지 갤러리·순환 저장(최근 10개)
- self-restart(NPU 누수 우회), 모델 화이트리스트/스위칭 UI

> 이유: 이것들은 전부 **카메라 안에서 돌기 때문에 필요했던** 장치들이다. PC에서는 해당 제약이 없다.

## 10. 구현/디버깅 시 반드시 알아야 할 함정 (gotchas)

1. **onnx 출력이 decoded인지 raw인지** — 첫 프레임 로그로 확인. 대부분 표준 export는 decoded(=NMS만). 아니면 `infer_mode="raw"`.
2. **전처리 dtype** — onnx가 float면 `/255`, uint8이면 그대로. (`detector.py`가 세션 input type으로 자동 판별하나, 정확도 이상 시 여기부터 의심.)
3. **letterbox vs stretch** — 기본 letterbox(비율 유지, 좌표 역변환 포함). 카메라는 stretch였음. 박스 위치가 어긋나면 이 설정부터 확인.
4. **L_L write 스킵** — 정상 복귀 시 PLC가 이전 코드에 latched. 컨베이어 동작 확인 후 `write_zero_on_normal` 결정.
5. **XGT는 thread-safe 아님** — 추론 루프에서 단일 스레드로만 호출. 대시보드(후속)에서 별도 스레드로 PLC 접근 시 lock 필요.
6. **RTSP 지연/버퍼** — `CAP_PROP_BUFFERSIZE=1` + 최신 프레임 우선. 지연 누적되면 여기 확인.
7. **area_ratio 분모** — 현재 ROI polygon 미사용이라 **프레임 전체 면적**이 분모. ROI를 넣을 경우 분모를 polygon 면적으로 교체(Shoelace)해야 임계값 의미가 설계와 일치.
8. **PLC 게이트** — `use_plc_gate=True`면 D8000&D8001 둘 다 1일 때만 판정. 기본 off.
